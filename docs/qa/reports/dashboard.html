▸QF-SEC-001 P1 AUTH Admin login has no brute-force/rate-limit protection Fixed
FIXED — admin/login.php now calls rate_limit_check('admin-login', 15, 10) before checking credentials, showing "Too many login attempts" past the threshold. 15/10min (not the public-form default of 5) so one shared office IP with several staff signing in doesn't get falsely locked out; a brute-force attempt against a bcrypt hash is still fully defeated well below that rate. Verified live via curl (blocked on the 6th-and-later of 7 rapid attempts before the threshold was widened, then reconfirmed at 15) and via an isolated regression test, tests/e2e/admin-login-rate-limit.spec.js (kept in its own file since it deliberately exhausts the quota and would otherwise block other tests' logins in the same run).
▸QF-SEC-002 P1 AUTH Session cookie missing HttpOnly flag Fixed
FIXED — ini_set('session.cookie_httponly', '1') added before session_start() in config/config.php, config.sample.php, and config.railway.php (the file Railway's Dockerfile actually deploys). Verified live via curl -I on /admin/login.php: Set-Cookie now includes HttpOnly. Regression test in tests/e2e/admin-auth-rbac.spec.js.
▸QF-SEC-003 P2 AUTH Session cookie missing Secure and SameSite flags Partially Fixed
SameSite FIXED — ini_set('session.cookie_samesite', 'Lax') added alongside the HttpOnly fix, verified live via curl. The Secure flag was deliberately deferred: setting it requires correctly detecting HTTPS behind Railway's proxy from this local/offline environment, and getting that detection wrong risks locking out admin login in production (a cookie marked Secure is silently dropped over any connection the browser doesn't consider HTTPS). Recommended next step: add the Secure flag right after the next production deploy, verified live against the real Railway domain rather than guessed at from here.
▸QF-SEC-004 P2 DATA No .htaccess in uploads/ blocking PHP execution Fixed
FIXED — added uploads/properties/.htaccess and uploads/documents/.htaccess (Require all denied on .php/.phtml, matching the root .htaccess's pattern). Confirmed the Dockerfile already sets AllowOverride All, so these take effect, and docker-start.sh's uploads-seed copy uses cp -rvn (no-clobber), so the new .htaccess files will land in the existing production volume on the next deploy without needing a manual step. Verified live: requesting a .php file under either directory now returns HTTP 403 (was previously whatever the file would have executed as). Regression check added to tests/backend/security-completion.php (QF-SEC-004-properties / QF-SEC-004-documents).
▸QF-UX-001 P3 RBAC Settings sidebar link shown to non-owner roles Fixed
FIXED — includes/admin-header.php now wraps both the "Settings" section label and the Settings link in the same role === 'owner' check already used for Manage Admins, so agent/admin users no longer see a link that would 403 for them. settings.php's own server-side require_role('owner') was already correct and unchanged. The existing QF-UX-001 Playwright test (previously a soft annotation-only check) was converted to a hard assertion and confirmed passing.
▸QF-COMPAT-001 P2 COMPAT Compare toggle buttons fail to register clicks on Firefox, WebKit, and mobile emulation (Chromium unaffected) Partially Fixed
ROOT CAUSE FOUND AND FIXED for the real bug: the compare-toggle icon is an inline SVG with fill="none" (stroke-only), and browsers differ on whether a click through its unpainted interior counts as hitting the icon or falling through to the card underneath — on Firefox this caused the click to fall through to the property card's own link and navigate away mid-test instead of toggling compare. Fixed with .compare-toggle svg { pointer-events: none }, forcing every click to resolve to the button itself regardless of engine. Also changed the hover effect from transform: scale() to box-shadow, removing a geometry change that could affect click-target stability. Confirmed fixed on chromium-desktop, firefox-desktop, and mobile-android (Chromium-based) — all pass cleanly now. REMAINING (webkit-desktop, mobile-ios — same WebKit engine): Playwright still reports "element is not stable" here. Investigated with a diagnostic (a fixed 5-second wait before clicking resolves it every time), which confirms this is Playwright's own conservative synthetic-click heuristic reacting to the page's legitimate scroll-triggered entrance animation (cards fade/slide in via GSAP the first time they scroll into view) — not a functional defect. A real tap isn't gated by that heuristic; browsers hit-test wherever a finger actually lands, animating or not. Tried two test-side mitigations (scroll-and-wait, wait-for-opacity) — neither fully resolved WebKit's timing without adding new flakiness elsewhere, so rather than keep chasing a test-tool artifact, this is left documented rather than 'fixed': WebKit/Safari users should be spot-checked manually rather than relying on this automated signal.
▸QF-NFR-401 P3 COMPAT Firefox accessibility scan inconclusive on this machine (environment issue, not a product finding) Env. Limitation
NOT FIXABLE VIA CODE — headless Firefox crashed during axe-core injection on this machine (RenderCompositorSWGL graphics error), a known headless-Firefox-on-Windows GPU compatibility issue unrelated to Kutumb's code. There is no application change that addresses this; it needs either a different test machine/CI runner or a manual Firefox spot-check instead of the automated a11y scan.
